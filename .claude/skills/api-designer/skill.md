# API Designer — API 설계·문서화·목업·테스트 파이프라인

API의 설계→스키마→문서→목업·테스트를 에이전트 팀이 협업하여 한 번에 생성한다.

## ⚠️ 이 레포에 맞게 고쳐 쓴 버전이다

원본 스킬은 `schema-validator` / `doc-writer` / `mock-tester` / `review-auditor` 4명을
전제하는데 **이 레포에는 없다.** 없는 에이전트를 Agent 도구로 부르면 실패한다.
아래 구성으로 대체한다.

그리고 이 레포에서 **OpenAPI 스키마는 손으로 쓰는 산출물이 아니다.** FastAPI가
`app/schemas/`의 Pydantic 모델에서 생성하고, `pnpm generate:api-types`가 TS로 내려받는다.
따라서 "스키마 YAML을 작성한다"는 단계는 무효이고, 그 자리에 **Pydantic 모델 작성**이 온다.

## 실행 모드

**에이전트 팀** — 아래 4명이 순차·병렬로 협업한다. 규모가 작으면 api-architect 단독도 가능하다.

## 에이전트 구성 (이 레포에 실제로 있는 것)

| 에이전트 | 파일 | 이 파이프라인에서의 역할 |
|---------|------|------|
| api-architect | `.claude/agents/api-architect.md` | 엔드포인트·요청/응답 형태 설계 |
| ml-dev | `.claude/agents/ml-dev.md` | 모델이 실제로 받는 입력 형태 확정 — **요청 스키마의 근거** |
| backend-dev | `.claude/agents/backend-dev.md` | Pydantic 모델·라우트 구현, pytest |
| architect | `.claude/agents/architect.md` | 설계 결정 1·API 계약 규칙과의 정합성 검증 |

`frontend-dev` / `api-integrator`는 생성된 타입을 소비하는 쪽이라, 계약이 확정된 뒤에 부른다.

## 워크플로우

### Phase 1: 준비 (오케스트레이터 직접 수행)

1. **중간 산출물은 스크래치패드에 쓴다.** `_workspace/`는 gitignore 대상인 **세션 인계용**
   디렉토리이지 작업 파일 자리가 아니다 — 다음 세션에 넘길 문서만 번호를 붙여 남긴다
2. 현재 상태를 읽는다:
   - `packages/ear-dream-api/app/schemas/` — 지금의 계약
   - `packages/ear-dream-api/app/api/v1/` — 지금의 라우트
   - `packages/core/src/types.ts` — 프론트가 쓰는 별칭
   - Notion 「API 명세서 (MVP)」·「MVP 아키텍처 및 개발 로드맵」 — 의도
3. **패러다임·인증을 묻지 않는다.** REST, 인증 없음으로 고정되어 있다
4. 바꾸려는 것이 **필드 추가**인지 **재설계**인지 먼저 판정한다.
   재설계면 프론트 영향 범위를 함께 파악한다

### Phase 2: 실행

| 순서 | 작업 | 담당 | 의존 |
|------|------|------|------|
| 1 | 모델 입력 형태 확정 (어떤 랜드마크를 몇 프레임, 정규화 기준) | ml-dev | 없음 |
| 2 | 엔드포인트·요청/응답 설계 | api-architect | 1 |
| 3 | Pydantic 모델 + 라우트 구현, pytest | backend-dev | 2 |
| 4 | 정합성 검증 | architect | 2, 3 |

**1번을 건너뛰지 말 것.** 모델 입력을 모른 채 요청 스키마를 정하면 그게 그대로 굳고,
나중에 어긋난 것을 발견했을 때는 이미 그 형태로 학습 데이터를 모은 뒤다.

### Phase 3: 반영

1. `pnpm generate:api-types` 실행 — 이걸 빼먹으면 프론트 타입이 서버와 어긋난 채로 남는다
2. `pnpm typecheck`와 `pnpm test:api` 통과 확인
3. 확정된 계약을 Notion 「API 명세서 (MVP)」에 반영 (문서보다 코드가 정본이므로 코드가 먼저다)
4. 미확정으로 남긴 항목을 `[확인필요]`로 명시해 보고한다

## 작업 규모별 모드

| 사용자 요청 패턴 | 실행 모드 | 투입 에이전트 |
|----------------|----------|-------------|
| "인식 API 재설계해줘" (모델 입력이 바뀜) | **풀 파이프라인** | ml-dev → api-architect → backend-dev → architect |
| "엔드포인트 하나 추가해줘" | **증분 모드** | api-architect → backend-dev |
| "이 스키마 문제 없나 봐줘" | **검증 모드** | architect 단독 |
| "지금 계약이 프론트에서 쓸만한지 봐줘" | **소비자 검증** | frontend-dev 또는 api-integrator |

**모델 입력 형태가 바뀌는 변경이면 반드시 풀 파이프라인이다.** 스키마만 고치면
학습 코드와 어긋나고, 그 어긋남은 "학습은 잘 됐는데 실사용은 틀림"으로 나타나 추적이 어렵다.

## 데이터 전달 프로토콜

| 전략 | 방식 | 용도 |
|------|------|------|
| 코드 | `app/schemas/`의 Pydantic 모델 | **계약의 정본.** 문서가 아니라 여기가 기준이다 |
| 메시지 기반 | Agent 응답 / SendMessage | 설계안, 수정 요청 |
| 태스크 기반 | TaskCreate/TaskUpdate | 진행 상황 추적 |

레포에 중간 산출물 파일을 만들지 않는다. 필요하면 스크래치패드를 쓴다.

## 에러 핸들링

| 에러 유형 | 전략 |
|----------|------|
| 모델 입력 형태 미확정 | **스키마를 확정하지 않는다.** 무엇이 미정인지 명시하고 멈춘다 |
| 성능·정확도 목표 미확정 | `[확인필요]`로 두고 임의 숫자를 넣지 않는다 |
| 에이전트 실패 | 1회 재시도 → 실패 시 누락을 명시하고 진행 |
| 설계 결정 1과 충돌 | architect에게 판단 요청. 임의로 프론트 전처리를 넣지 않는다 |
| 기존 계약을 깨는 변경 | 재설계로 판정하고 프론트 영향 범위를 함께 보고 |

## 이 프로젝트의 실제 사례

### 인식 요청 스키마 재설계 (진행 중)
현재 `RecognizeRequest`는 프레임당 손 하나(`window: list[HandFrame]`)만 담는다.
그런데 손 선택은 서버가 하고, 정규화 기준으로 어깨가 필요하고, 얼굴도 함께 간다.
즉 **필드 추가가 아니라 재설계**다. 요청에 실려야 하는 것:
양손 + handedness 라벨/score + 얼굴 + 포즈(어깨) + 프레임별 타임스탬프 + `sourceWidth`/`sourceHeight`.

해상도가 필요한 이유 — MediaPipe 정규화 좌표는 x를 너비로, y를 높이로 나눈다.
x·y를 섞는 모든 거리 계산이 종횡비에 의존하므로, 카메라 구도가 바뀌면 그 전에 모은
학습 데이터의 특징값이 통째로 이동한다.

### 페이로드 크기
손만 30프레임이면 30×21×3 ≈ 1,890 float라 반올림 + gzip으로 수 KB다.
얼굴 원본을 더하면 30×478×3 ≈ 43,020으로 23배가 된다.
전량 전송할지 지점 부분집합만 보낼지는 **학습 시작 전에** 정해야 한다(목록이 바뀌면 재학습).
